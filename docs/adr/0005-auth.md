# 0005 — Auth: our own small module on Node crypto, sessions in Postgres

- **Status:** accepted
- **Date:** 2026-11-01
- **Feature:** M2-01

## Context
M2 needs email + password accounts: sign-up, sign-in, sign-out and password reset, sessions in
Postgres, an http-only cookie, rate limits and nothing secret in logs (`CLAUDE.md` privacy).
Constraints: web is UI only and reaches the api through the generated client (ADR 0002); the
api runs as `stirred_app` under row-level security (ADR 0003); no paid vendor, no lock-in;
errors never reveal whether an email has an account (M2-02).

## Options
### A — An auth library (better-auth, Lucia's successors, Auth.js)
Feature-rich (OAuth, 2FA later). They bring their own tables, ORM adapters and handlers that
expect to own the request, which fights the per-user transaction and RLS of ADR 0003 and the
web/api split; a large dependency for four endpoints. Lucia itself is deprecated (2025) in
favour of "write it yourself" guides.
### B — A hosted identity provider (Auth0, Clerk, Cognito, Supabase Auth)
Least code; costs money past a free tier, holds users' emails off-site and locks the user table
to a vendor. Needs a human decision (money, privacy).
### C — Our own module on `node:crypto` (chosen)
`scrypt` for passwords, 32-byte random tokens stored as SHA-256, plain SQL tables under RLS.
No new dependency. We own the edge cases, so they are listed below and tested.

## Decision
C. The whole surface is four flows; the crypto is Node's (OpenSSL), and owning the tables keeps
ADR 0003 intact. Reversal: the api's `auth` module is the only caller; a library can replace it
behind the same endpoints, and users keep their hashes if it supports scrypt.

**Passwords.** scrypt, N = 2^16, r = 8, p = 1 (64 MiB; OWASP Password Storage Cheat Sheet),
16-byte salt, stored as `scrypt$N$r$p$salt$hash` so parameters can rise later. 10 to 128
characters, no composition rules (NIST SP 800-63B: at least 8, no composition rules; we ask
10). A sign-in for an unknown email still runs one scrypt, so timing does not tell.

**Sign-up confirms the address and never reveals an account.** Sign-up answers the same
`202 check-email` for every address and mails a one-use link (24 h). The pending password hash
travels in the link's token row, not on the user. Confirming needs the link **and** the password
typed at that sign-up (checked against the row's hash; a link is spent on its first use, right
or wrong): only then is the user created (or, for an address that already has one, given that
password, like a reset) and signed in. A link someone else asked for, with their password,
claims nothing even when the mailbox owner opens it (review finding, M2-01).

**Sessions.** A random 32-byte token, given once to web; Postgres keeps only its SHA-256 with
`expires_at` (30 days, absolute). Web keeps the token in an http-only, `SameSite=Lax`, `Path=/`
cookie (`Secure` off localhost) and sends it to the api as `Authorization: Bearer` from server
code (M2-02 builds that). Sign-out deletes the row; a password reset deletes all of the user's
sessions.

**Reset.** Answers `202` for every address; the lookup, link and mail happen after the answer,
so a known address answers no slower. The one-use link (1 h) goes only to an existing account.
Using it sets the new password, ends every session and signs in.

**Isolation.** `app_user` and `session` carry the ADR 0003 policy. The steps that run before a
user id exists (find a user by email, find the user of a session token, take a one-use token)
are `security definer` functions owned by `stirred_owner` that return only what the step needs;
`auth_token` has RLS with no policy, so the api role reaches it only through them.

**Rate limits.** In-process fixed windows per api instance (sign-in 10 per 15 min per email,
30 per 15 min per client across sign-in, sign-up and reset, the client address taken from the
`X-Forwarded-For` entry added by web, the one trusted hop; sign-up and reset 5 per hour per email): enough for one instance;
a shared store is needed before running several. Keys stay in memory and are never logged.

**Email.** A `Mailer` port in the api. Local and verify stacks use Mailpit (a container that
catches mail; UI on 127.0.0.1:8325); tests use an in-memory outbox. The production provider
costs money and is chosen at deploy (M3-04, needs-human). Mail bodies and addresses are never
logged.

## Consequences
- No OAuth, magic links or 2FA in M2; each would be its own feature on these tables.
- One more container locally (Mailpit). The api refuses to start without `MAIL_URL`.
- Per-instance rate limits must move to Postgres or a shared store before horizontal scaling.
